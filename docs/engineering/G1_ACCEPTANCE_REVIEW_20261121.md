## Recovery verification hardening

The former fixed list of tables in PostgreSQL restore CI could miss newer source tables. PR #4 discovers actual migrated tables from the catalogue, requires restoration of all pre-existing tables, and checks stored row digests in preserved tables. It also verifies unaffected sequence states and explicitly distinguishes restore-quarantine state changes (session revocation, identity/share invalidation, key rotation, and related event state) from preserved business/evidence records. The quarantine-altered tables must continue to pass `db/tests/restored_database_gate.sql` and `db/tests/full_security_gate.sql`.

A verified prior run logged `restore_catalog_verified preserved_tables=76 quarantine_mutable_tables=17 sequences=1`. Those counts describe that synthetic fixture on that SHA, not an enduring schema specification. Audit the manually enumerated quarantine-exception list whenever restoration behaviour changes. Logical dumps and current checks do not constitute a complete PITR, storage/secret escrow, real-world RPO/RTO, or disaster recovery demonstration.

## Blocking exit criteria

1. Reconcile the latest moving G1 parent branch without discarding concurrent changes; review PR diff and resolve conflicts without auto-merging.
2. Require all applicable workflows to pass against the **exact final review SHA**, including the added JOIN/GUC negative regression, and confirm database restore output in the job log.
3. Record final acceptance-to-test traceability with independent reviewer signoff for least privilege, SECURITY DEFINER boundary, transaction-pool isolation, recovery quarantine, evidence provenance and immutable-audit caveat.
4. Keep `main` and production untouched until explicit approval. Existing CI is synthetic verification only; lack of production identity/key lifecycle, load tests and independent review is not cured by a passing build.
