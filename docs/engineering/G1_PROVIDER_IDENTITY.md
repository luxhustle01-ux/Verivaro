# Provider-bound authentication gateway

The gateway verifies pinned HTTPS issuer, single client audience, RSA signing keys (RS256, explicit kid), signed nonce, provider-configured ACR and AMR requirements, auth_time freshness (240 seconds), token validity and duplicate JSON claims. MFA semantics must be independently confirmed for the actual provider; these claims alone do not prove a specific factor or phishing resistance. The signed upstream subject is hashed and mapped to a preprovisioned local actor, never matched to email or caller-supplied actor ID. A separate provisioner role is required; one irreversible binding per actor in this initial design. Disabling a binding disables the actor and invalidates sessions. Direct registration is no longer granted to the identity service. Login challenges use 256-bit nonce and independent binding, stored as digests, scoped to issuer/audience, atomically consumed with local session creation, five-minute expiry, 120 starts/minute global and 4096-row cap. Gateway signs a local RS256 session token bound to registered sid, no more than 15 minutes and no later than upstream token expiry; logout revokes that session. Restore deletes challenges and includes bound actors in quarantine.

This is a backend authentication core, not a complete browser OIDC flow. The caller must be a trusted backend that owns the binding secret, performs authorization-code exchange with PKCE and state validation, and obtains the ID token directly from the provider. Do not expose exchange as an arbitrary bearer-token login endpoint. No discovery/JWKS fetching, browser redirect/callback, cookie/token storage, refresh, real provider signup, live provider logout/event delivery or production deployment yet. Provider keyset catalogues must use deterministic UTF-8 JSON encoding equivalent to `Buffer.from(JSON.stringify(catalogue))`: correctly signed catalogues with duplicate keys, escaped aliases, alternative number representations or extra whitespace are rejected to prevent ambiguous parsing. Pinned keys require controlled rotation. The verifier now requires a separately trusted, **durable compare-and-swap checkpoint writer** for each keyset rotation. Rotation is asynchronous and blocks token verification while the checkpoint is being committed. If durable persistence is uncertain, verification fails closed until restart with a trusted checkpoint. Without the writer, rotation is denied; startup still requires an independently trusted checkpoint. CI verifies the rotation state machine using synthetic fixtures; the separate `provider-checkpoint-store.mjs` adapter now also exercises real local disk persistence, atomic replace, exclusive single-process lease, restart, and rejection of malformed or stale checkpoints. **Local disk does not constitute an independent anti-rollback authority, production KMS or multi-node consensus.** No paid services. The database trusts the dedicated gateway to validate signatures and MFA before redeeming. Provisioning and credential handling remain trusted administrative boundaries. The subject digest is pseudonymous, not anonymized. CI uses locally signed synthetic ID tokens and real PostgreSQL, not external provider accounts.


**Witness-backed verifier integration:** `provider.verify()` may be asynchronous. The gateway awaits the verified provider claims before reading the nonce and redeeming the challenge; rejected or unavailable witness checks cannot create a local session. The direct gateway caps pending exchange verifications (default 8, configurable 1–32) rather than queueing excess requests. Existing synchronous pinned providers remain supported. This does not cancel an already pending witness request; operators must independently enforce bounded witness network I/O and capacity/availability budgets.
