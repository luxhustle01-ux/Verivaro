# Browser authentication boundary

Fixed HTTPS application origin and same-origin-to-issuer configured HTTPS authorization/token endpoints; server-side confidential-client authorization-code exchange (client_secret_basic), PKCE S256, query callback with mandatory RFC 9207 issuer, exact redirect URI, one-time state bound to an independent browser cookie, fresh nonce, configured MFA policy and existing local session registration. Login and logout are POST with exact Origin; no arbitrary redirects, no tokens in URLs or response body. Host-only Secure HttpOnly SameSite=Lax cookies contain only random opaque handles. PostgreSQL stores hashed handles, encrypted AEAD flow credentials and encrypted local token, with per-purpose/handle AAD and separately configured 32-byte key. Callback deletes state atomically before token request; failure requires restarting login. Existing active session must be explicitly logged out before login/account switch. Local sessions expire under the already enforced provider policy, are checked against database revocation and disable state, and logout atomically removes the opaque session and revokes the local session. Recovery deletes both browser tables. Single configured issuer/client, no refresh or provider-wide logout; active browser sessions are bounded at 10000 and stale records cleaned on insert, flow rows bounded at 4096. Global challenge admission is separately bounded; deploy edge and per-peer rate limits, TLS termination and access-log redaction for callback query strings. Cookie flags are emitted and checked in real HTTP CI, not browser-engine behavior. Tests use manually supplied cookies and injected synthetic HTTPS provider responses, real PostgreSQL and real HTTP; no external provider account or deployment. Real provider must support RFC 9207, PKCE, confidential client auth, confirmed ACR/AMR and fresh authentication. Provider endpoints and secrets must be independently approved and protected, token HTTP requests have timeout and response cap, redirects rejected. Key rotation invalidates stored encrypted browser sessions unless migrated; rotate through controlled session reset. The module exports handler and resolveSession for integration with a future HTTPS application runtime, not a standalone deployed login website. No real user data or paid service used.


**Asynchronous witness verification:** The browser callback awaits the provider verification result before checking the returned nonce and before asking the gateway to redeem the login. The gateway then independently verifies again and awaits that second check; neither verification should be skipped. Browser request concurrency is bounded by `maxConcurrent` (default 8), and direct gateway exchanges have their own bounded admission (default 8). A witness outage or rejection must deny callback/session registration. External witness latency and transport timeouts are deployment dependencies; the application cannot assume those are supplied by an in-memory synthetic witness.
