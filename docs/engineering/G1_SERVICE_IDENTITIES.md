# Service identity and connection isolation

All five application database adapters now share a fixed role/login guard. Each checkout discards old session state, forces pg_catalog search path, rejects elevated or inherited login/group attributes, extraneous direct or transitive memberships, ADMIN OPTION, database CREATE and schema CREATE. A distinct dedicated login must have only intended group membership (NOLOGIN group) and no direct application table/column/function/schema access. Mandatory expectedLogin pins the exact dedicated login and disallows using the group as a login; provision distinct nonprivileged NOINHERIT login per service/replica. All live application adapter fixtures use dedicated logins. Historic standalone SQL regression fixtures are isolated and revoked before application tests. This is a guard against misconfiguration, not defense against a malicious DBA, compromised host, or a race after privilege checking.

Monitor worker, reader and alert launcher now requires private owner-only password file VV_DB_PASSWORD_FILE, explicit PGHOST/PGUSER/PGDATABASE, and an independent PEM CA file VV_DB_CA_FILE for TLS with certificate verification and DNS hostname. No environment PGPASSWORD, PGOPTIONS, connection-string or TLS override. Explicit VV_ALLOW_LOCAL_PLAINTEXT=1 is reserved for literal loopback isolated tests. Use distinct credentials, restrictive file ownership and trusted path ancestors; restart processes on credential rotation and revoke/terminate old logins explicitly. TLS wiring is exercised in the separate live TLS CI fixture; production PKI and external certificate rotation remain unverified. Password strings necessarily exist in process memory; file-based delivery is not a vault. No live service deployed. PostgreSQL grants, database/schema ACLs and external provisioning still require independent review. Real CI tests grant and revoke synthetic adverse permissions and check denial before admission operations.


## Private secret ancestor checks (G1 hardening; draft-only)

In addition to O_NOFOLLOW on the target inode and a 0600, same-UID file check, `readPrivate` now validates the **entire existing absolute path ancestry**. It rejects symlinked intermediate directories, dot/dot-dot or repeated components, directory ownership outside root/current service UID, and group/world-writable ancestors. A root-owned sticky directory (such as `/tmp`) is allowed solely so owner-only disposable CI fixture subdirectories can be used. The target file is rechecked against its open inode and file metadata after reading. This validation must not be represented as resistant to a same-UID compromised process or a malicious administrator: protect ancestor directories and private bind mounts with the OS, and block any untrusted filesystem actor with sufficient privileges to rename service-owned directories. The startup loader never logs secret file contents or credential paths. New regression tests cover ancestor symlinks, world/group write, and legitimate protected nested paths.


## PostgreSQL 16 SET / INHERIT grant enforcement

The service identity preflight validates each direct membership using **all three PostgreSQL 16 membership options**, not just `MEMBER` or `NOT ADMIN`: `INHERIT FALSE`, `SET TRUE`, `ADMIN FALSE`. This prevents a `SET FALSE` service login from passing startup despite being unable to activate its restricted NOLOGIN group, and prevents accidentally granting ambient inherited service permissions through a direct `INHERIT TRUE` edge. A full catalog membership inventory, login/role attributes, direct schema/table ACLs, session cleanup and database enforcement remain mandatory. Real disposable PostgreSQL tests replace the intended membership with the unsafe options, assert refusal at the connection admission boundary, then restore the exact safe grant. This is a G1 candidate safeguard, not external security sign-off or evidence of production deployment.


## Cross-schema login-level ACL and future-grant drift gate (G1 draft)

The shared `assertServiceLogin` startup check now rejects **explicit direct ACL entries and owned objects** on the dedicated login, in addition to group-role membership controls. The read-only catalog checks cover non-system schema grants/ownership, all relation kinds (including sequences), functions, types, database direct ACLs, and `pg_default_acl` grants on *future* objects. It does **not** misclassify ordinary `PUBLIC` privileges as login-specific grants. It also checks grants outside schemas whose names start with `verivaro` (for example `public`), which could otherwise leave independent authority on the login before `SET ROLE`.

A real disposable PostgreSQL 16 integration suite now injects, then revokes, explicit schema USAGE, database CONNECT, sequence USAGE, custom enum type USAGE and `ALTER DEFAULT PRIVILEGES` SELECT grants. Each must reject the login directly and reject an application admission request, then pass again after cleanup. This is a defense against accidental direct grants at connection checkout; it is **not** protection against subsequent DDL performed by a privileged administrator between the check and a database operation, and it is **not** a complete audit of every PostgreSQL privilege-bearing object class or external security certification.

## Database-wide startup defaults and credential-rotation gate (draft G1)

The shared service-login guard now rejects any `ALTER DATABASE <connected_database> SET` overrides in `pg_db_role_setting` (the `setrole=0` row), in addition to per-login/group `ALTER ROLE ... SET` configuration. This is a deliberate **zero per-database overrides** policy. It prevents database-wide defaults from silently changing service connection behaviour across replicas. The guard checks current catalogue state on every validated checkout, not only new PostgreSQL connection establishment; it is not protection against a privileged concurrent DDL race or cluster-wide administrator configuration.

The separately privileged, explicitly confirmed credential-retirement operation also blocks role-level and database-wide startup overrides for the old/replacement logins and their group before retiring the old identity. PostgreSQL 16 disposable integration tests inject and reverse these settings, assert fail-closed admission and denied retirement, then verify recovery. This is only a narrow parity improvement: the retirement preflight still needs a separate complete policy-equivalence review against `assertServiceLogin` before production credential rollover can be approved. No production credentials or Neon write operations were used.

## Shared admission/retirement catalogue policy — draft G1

Credential retirement now uses exactly the same **read-only PostgreSQL privilege predicate** as live service admission, avoiding separate hand-maintained allowlists. The shared inspection checks direct grants, owned databases and other objects, PostgreSQL 16 role membership options, service-group database/schema CREATE, parameter ACLs, and role/database startup overrides. Retirement has its own explicit confirmation and replacement-expiry checks; admission independently enforces the connected `current_user=session_user` invariant. The privileged retirement transaction pins `search_path` to `pg_catalog` to prevent operator-session path contamination.

Disposable PostgreSQL/TLS regression tests verify that direct parameter and system-function grants, service-group database CREATE and parameter grants, and a different database owned by the replacement all block retirement *without disabling the old login*. A subsequent clean attempt retains the explicit rotation contract and terminates old sessions. This shared policy reduces catalogue-check drift; it does not attest to production TLS/client identity, prevent a privileged administrative race, or replace independent DBA/release approval. Any change to the shared predicate must rerun both admission and retirement integration tests.
